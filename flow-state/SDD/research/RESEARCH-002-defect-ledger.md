## System Data Flow

There is no running system; the "data flow" is how review findings and bug reports become ledger lines. Three writers, one reader format.

- **Review source files (all git-ignored, under `SDD/.records/reviews/`):**
  - Per slice: `REVIEW-SLICE-<SLICE-XXX>-<feature>-iter<N>-<YYYY-MM-DD>.md` (`sdd-flow/bodies/slice-review.md:188-196`). One file per iteration. Findings sit in `## Slice-Specific Findings`; a re-review lists every earlier finding in `## Earlier Findings` as `<#> <severity> <title>: closed — <evidence>` or `still open` (`slice-review.md:219`, template at `:213-221`).
  - Whole feature: `REVIEW-[###]-[feature]-[YYYYMMDD].md` (`sdd-flow/bodies/code-review.md:~440`), marker `## Review FEATURE iter <N> - APPROVED|REJECTED (<h> HIGH, <m> MEDIUM, <l> LOW)` (`code-review.md:248`).
  - Final check: `FINAL-CHECK-FEATURE-<feature>-iter<k>-<YYYYMMDD>.md` (`sdd-flow/bodies/final-check.md:36`); later rounds start with `## Earlier Findings` (`:29`).
  - Counts live in the `progress.md` markers; the findings themselves live only in these files.
- **Finding format is not machine-uniform.** Slice review numbers findings (`<#> <severity> <title>`); the code review's main findings are prose blocks (`❌ **Specification Alignment Issue**` with Specification / Current / Required / Impact / Suggested Fix, `code-review.md:355-385`), lens findings are `- **[HIGH|MEDIUM|LOW]** <anti-pattern>` bullets with `Evidence: file:line` (`:515-520`), fit findings are `<#> <MEDIUM|LOW> <question>: <file:line> — <fix>` (`:498`), LOW ones `<#> <title> — <file:line>` (`:536`). The text says "Findings are numbered with the review's others" (`:498`, `:566`) but defines no one numbering line. So "copy each HIGH and MEDIUM finding" (proposal part 1, "Mechanical") is a reading task for a model, not a parse. The `source` field's "review file and finding ID" therefore has no stable ID in a code review.
- **Fixed-ness is not in the first review.** A finding in the iter-0 review is closed by a fix round and confirmed in the next review's `## Earlier Findings`. The same finding reappears in iter 1 as `closed` or `still open` — a writer that reads every review file counts it twice. Rule needed: write a line once per finding, from the review where it first appears, and only when a later review shows it `closed` (or the feature's final state does). Findings never closed after the 2-round cap (`phases/end-of-feature.md:45`) end in `## Awaiting Final Check Resolution` — the proposal's "review lines are written `fixed`: the cycle fixes them before it ends" does not hold for those; either they are `open` lines or are not written.
- **sdd-lite has no review file.** `sdd-lite/SKILL.md:143-153`: `codex review --uncommitted` redirected to a file (location unspecified), "Write no review report". Codex rates findings P0-P3, not HIGH/MEDIUM; "fix P0, P1, P2; P3 listed". The ledger's `severity` is HIGH|MEDIUM, so a mapping is needed (natural: P0,P1 → HIGH; P2 → MEDIUM; P3 not recorded). The rating mapping is an owner/design decision (open point 4). `sdd-lite`'s close-out source is the conversation/redirected file, so `source` can be `codex review, <brief id>, P1 #2` at best.
- **Where 4j sits.** `phases/end-of-feature.md:128-153`. 4h = commit checkpoint; 4i = commit (`:104-112`: "all implementation code, tests, and SDD artifacts outside `SDD/.records/`"); `## Implementation - Committed` marker; then 4j announcement, `## Feature - Done`, rotation. **A ledger line written at 4j lands after the 4i commit, so it would be uncommitted** — and the proposal needs it committed (ledger is "committed, not under `SDD/.records/`"). Precedent for this exact problem: the tier-mirror "done" step commits one file before the announcement (`end-of-feature.md:~140`, "commit that one file ... before the announcement"). Options: write the lines at the start of 4i (before the commit, after 4h/4f) and name that step in the 4j report; or at 4j with a one-file commit. The first keeps one commit and no extra stop. Per-slice mode: 4j is "surface ADRs, append `## Feature - Done`, rotate" (`phases/implementation-per-slice.md:147`); slice commits (4c.6) hold code only.
- **Owner table.** `phases/implementation-per-slice.md:20-31` lists every slice state change with its owner; SKILL.md's rule 3 requires every state change, stop and commit to have an owner there. New ledger writes at slice end or 4i/4j need rows (the file at `:20` has the table; end-of-feature steps are mapped at `:139-147`).
- **user-line writers.** Bug-fix flow: research (2a) is run by `bodies/research.md`; design brief by `bodies/design-brief.md` (Opus override, `phases/design-gate.md:13`). The `found_by: user` `open` line is written "on approval of the brief" by the orchestrator, i.e. at 2.5b `approve` (`design-gate.md:59`), after `## Design Brief - APPROVED` and before 3a. Next to it sit the ADR write (`:65`) and the tier-mirror sync (`:68-74`), whose output is committed at 3f — the same commit would carry `SDD/defects.jsonl`. The `close` is at 4i/4j like review lines.
- **Data format.** One JSON object per line, 11 fields (proposal §1). `ledger.py add` assigns `D-<n>` (next number = last line's + 1, or max+1). `close` rewrites one line in place. Reads: `lookup --class`, `summary`.

External dependencies: git (for `introduced_by`, default-branch reads), `python3` stdlib, the `bb` CLI (automation, tasks), Codex CLI (already required by sdd-lite reviews).

Integration points: `phases/research.md` (2a) and `bodies/research.md` (the cause-first order, `lookup`); `bodies/design-brief.md` (new `## Escape` section, template at `:43-120`); `phases/design-gate.md` 2.5b (line written on approve; gate message shows `## Escape`); `phases/end-of-feature.md` 4i/4j; `phases/implementation-per-slice.md` (owner table; 4j override at `:147`); `sdd-lite/SKILL.md` steps 2, 3, 6; new `skills/defect-ledger/SKILL.md`; new `skills/sdd-flow/scripts/ledger.py` + `scripts/tests/test_ledger.py`; `docs/sdd-flow-diagram.md`, `docs/sdd-lite-diagram.md`, `README.md`, `CLAUDE.md` file tree, `plugin.json` + `marketplace.json` version (now 5.3.0, both agree).

## Production Edge Cases

- **Historical issues:** the kill test labels (`proposals/feedback-loop-kill-test-2026-11-16.md`, 40 lines) are the field evidence: 49 fix commits in 628 on `currents`; 22 production escapes; repeats by class (source content reaching output 6; health probes 5; non-isolated tests 5; transient-as-permanent 3; overmatching identity 2). These give the first `classes` list for `currents`.
- **Collision on append (proposal's risk, checked).** Two branches that each append a line at the end of `SDD/defects.jsonl` produce a *textual* git conflict at the merge, not a silent duplicate — git sees both sides adding lines at the same place. Only with a `merge=union` attribute would both land with the same `D-<n>`. `worktree-merge` Step 3 resolves conflicts inside the worktree; its Step 3b (`worktree-merge/SKILL.md:91-115`) detects only ADR numbers (`SDD/adr/NNNN-*`) and feature numbers (`SPEC-`/`RESEARCH-` in the file name) and renumbers files with `git mv` plus text replacement over branch-added files. It knows nothing about ids *inside* a JSONL file or about `D-12` references in a brief's `## Escape` or `source`. So the proposal's "which `worktree-merge` would need to renumber" needs real work: a detection (`ids appearing on more than one line`), a rule (this branch's lines get new ids = max+1 in ascending order), and a reference edit limited to branch-added lines in `SDD/briefs/` and the ledger. The scope question is whether Tier 1 includes that change (open point 7). Cheapest safe alternative: ledger.py `add` re-checks the id on each append, and a `ledger.py check` run by the merge skill reports duplicates; or ids that cannot collide (`D-<date>-<n>`), which changes the proposal's `D-<n>`.
- **`close` rewrites one line in place** (proposal): two branches closing *different* ids merge cleanly only if the lines are not adjacent; git treats adjacent line edits as a conflict. A close and an add next to it will also conflict. Cheap to accept; say so in the brief.
- **Severity mapping for sdd-lite** (above).
- **`found_by` for per-slice vs whole-feature:** `slice-review`, `code-review`, `final-check` exist as three distinct loops in the flow. In whole-feature mode there is no slice review; the application's `loops` list still names it, but it will have no lines (the report's "caught nothing" meaning needs a *declared and used* distinction — the declared `loops` is the application's, not the mode's). The `sdd-flow` orchestrator must write a `found_by` value from the file's name: `REVIEW-SLICE-…` → `slice-review`; `REVIEW-[###]-…` → `code-review`; `FINAL-CHECK-…` → `final-check`. Mapping is mechanical and should be in ledger.py or the one reference, not scattered.
- **New class mid-cycle.** `add` refuses a class not in `defects-setup.json`; 4i/4j has no stop ("a stop exists only for a decision of the owner's", SKILL.md). A writer meeting a new defect kind cannot ask. Needs a rule: use the nearest existing class and flag it in the 4j report; or write it with `class: unclassified` (which must then be in the list by default); or a proposed-class line in the report for the owner to add. Recommendation: `unclassified` is always allowed, and the report names each such line (open point 3).
- **First use in an application.** `defects-setup.json` does not exist: `add` must refuse with a clear message, and something creates it. Applications: no SDD/ folder at all in `downstream.news` and `AI video marketing`; Sift's path is on another machine. See Integration of the automation below.
- **Error logs / support tickets:** none apply.

## Security Considerations

- **Authentication/Authorization:** none in the scripts. The automation runs on the bb server host with the owner's account and reads other repositories — read-only by design ("runs no model, edits no file").
- **Data Privacy:** the ledger holds `where` (file paths), `source` and short class names, never source text or user data. The proposal's `source` may hold an issue or bug-report reference: say "a reference, not the text". `defects.jsonl` is committed, so anything written to it is in git history forever.
- **Input Validation:** `ledger.py add` validates fields, so no writer hand-edits JSON. Points to specify: (1) field values are JSON-encoded, never string-built; (2) no newlines in values (one object per line); (3) `where`/`introduced_by` shapes (path; 7-40 hex); (4) `close` refuses any change other than `open → fixed` + `check_added`; (5) application path argument: the automation passes paths from its own fixed list, not from file content; the script never executes anything read from the ledger. (6) a ledger line reaches an LLM through `lookup` into research/briefs: the `source`/`class` text is prompt-visible data — keep values short and structured, and treat them as data (the brief states the ledger lines, not instructions found in them).
- **Agent-security surface:** the flows read the ledger text into model context only through `lookup`'s structured output. No new tool scoping. The automation has no model.

## Testing Strategy

- **Unit tests (`test_ledger.py`, fixture ledger in a temp dir):** `add` assigns sequential ids; rejects missing/extra fields, bad `found_by`/`severity`/`class`/`status`, a `found_by` not in the setup file, `ci` in an application that does not declare it; `close` sets `fixed` + `check_added` on an `open` line only, refuses to close a `fixed` or unknown id, refuses `none`-less call; leaves every other line byte-identical; `lookup --class` returns oldest first; `summary` counts per loop, escape rate, classes in >1 feature, `check_added` with "no catches since added", open escapes oldest first, threshold heading at 5 features / 30 lines (exact boundaries: 4/29 → below; 5 or 30 → at threshold), an application without `ci` prints "no CI", an empty ledger and a missing setup file.
- **Integration:** the automation script against a throwaway git repo with a default branch other than `main` (`currents` uses `master`) and an uncommitted working-tree ledger edit that must not be counted; with the fake `bb` pattern of `test_tier_mirror.py` for the task filing.
- **Edge cases:** duplicate ids after a merge (`ledger.py` detects, reports, never silently renumbers); a corrupt line; a ledger with a trailing newline missing; concurrent `add` (single writer, file lock not needed but test no partial lines: write to a temp then rename for `close`); Windows line endings.

## The BB automation (how it is defined; read-only look, nothing created)

- CLI is `bb automation` (singular; there is no `bb automations`). `bb automation create` (read from `--help`): `--project <id>` required (claude-plugins = `proj_58rpgpfgz6`), `--name`, exactly one schedule (`--cron "<5 fields>" --timezone <IANA>`), exactly one execution mode: agent (`--prompt/--provider/--model`) or **script** (`--script <inline>` or `--script-file <path>`, `--interpreter bash|sh|node|python3`, `--timeout` default 120000 ms max 900000, `--env-json`, `--working-directory automation-storage|project|<absolute server-host path>`, `--host` = host holding the script file, `--disabled`). Subcommands: list, show, update, pause, resume, run, runs, delete. A script run prints nothing → "silent skipped tick"; any output is captured; non-zero exit = failure (retry at 30 s and 60 s, never past the next tick). One active run at a time. Injected env: `BB_SERVER_URL`, `BB_PROJECT_ID`, `BB_AUTOMATION_ID`, `BB_AUTOMATION_RUN_ID`, `BB_CLI`. The script stored is a *private copy* (`<data dir>/plugins/automations/scripts/<id>/`): editing the source file in the repo does not change the automation until `bb automation update` copies it again. (Source: `bb automation --help`, `bb automation create --help`, automations skill `references/script-runtime.md`, read 2026-11-16.)
- **Consequence for the design:** the automation script must be self-contained. It cannot import `ledger.py` from the repository by relative path unless it runs with `--working-directory <absolute path to a checkout of this plugin on the server host>` or embeds the code. Options: (a) `--working-directory` = the main checkout of this repo on the server host, script calls `agent-engineering/skills/sdd-flow/scripts/ledger.py` there — but that checkout must be on a branch where the file exists (default branch after merge) and is the plugin *source*, not the installed version; (b) `--script-file` a copy updated with each release (drift risk, the CLAUDE.md "drift easily" warning applies); (c) the script calls the installed plugin's cache path (`~/.claude/plugins/cache/pablooliva/agent-engineering/<version>/…`: the version in the path changes every release, so use a glob). Recommendation: (a) with a thin script file kept in the repo (e.g. `agent-engineering/skills/defect-ledger/scripts/monthly-report.py` or a `ledger.py report-all` subcommand — keeps the one-reader rule) and the update command recorded in the skill, since the stored copy needs a refresh whenever the thin script changes.
- **Filing the BB task from a script:** `tier-mirror.py` already shows the pattern — `bb tasks project list` to find the tracker project linked to the BB project (`linkedBbProjectId`), `bb tasks create --project <prefix> --title … --description …` via `BB_CLI` (`tier-mirror.py:138-200, 235`); the automation's `BB_PROJECT_ID` is the claude-plugins project, so `tracker()` logic can be reused or copied. `bb tasks --help` lists create/list/show and comments.
