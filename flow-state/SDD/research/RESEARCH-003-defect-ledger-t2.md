### DEFER-002 — renumber duplicate defect-ledger ids at worktree merge
- How ids are made: `ledger.py` `next_number` (:406) = max numeric part + 1; `cmd_add` :444-464 assigns `D-<n>`; `write` :367 replaces the file whole with the old text plus new lines at the end (so two branches each appending a line give a plain git conflict at the file end, as `defect-ledger/SKILL.md` ("Two branches that both changed the defect ledger ... resolve it by hand, keeping both lines") already says; with a union merge driver or hand-resolution both lines stay and the file holds two `D-5`).
- What refuses today: `parse_ledger` :284-309 raises "repeats the id of line N" for a repeated id, so every ledger command (add, close, lookup, reviews, and the monthly report section for that application) refuses until a human renumbers. The report shows `refused: ...` for that application only.
- Where ids are written outside the ledger file (the "briefs naming them"): the design brief's `- Ledger id: [D-<n> | none]` (bodies/design-brief.md:68), `## Escape Line - D-<n>` in `progress.md` (design-gate.md:90; `.records/` is git-ignored and not landed), the 4i close (end-of-feature.md:159-163, input `{"id": "D-<n>", ...}`), sdd-lite's brief field `Ledger id` (sdd-lite/SKILL.md:79; briefs land under `SDD/briefs/`). A `source` field holds an external reference, not a ledger id. Which committed files carry a `D-<n>` is therefore: `SDD/defects.jsonl` and briefs (`SDD/requirements/DESIGN-*.md`, `SDD/briefs/*.md`).
- How worktree-merge handles SDD numbering today: `worktree-merge/SKILL.md` Step 3b (:91-117) detects duplicate ADR numbers (`SDD/adr/NNNN-*`) and duplicate feature numbers (`SPEC-`, `RESEARCH-`...) across `git ls-files`, lists branch-added files via `git diff --name-only --diff-filter=A <target> HEAD`, shows the old → new mapping, and on a yes does `git mv` + replaces text only in branch-added files and only on branch-added lines in branch-modified files (`git diff -U0 <target> HEAD -- <file>`), re-runs detection, commits the renumbering as its own commit. Failure mode 12/13 (lines 29-30) name the two risks: landing duplicates, and renumbering the wrong side by blanket replace. It does not mention `defects.jsonl` at all. Ledger ids differ from ADR/feature numbers in that the duplicate is a line inside one shared file (not a file name) and the ids are reused in `close` lines that mutate an earlier line in place (a `close` on a target-side line is "branch-modified", a branch-added line is the only one safe to renumber).
- A `close` on a line that the other branch also closed or an `add` on both sides is the realistic collision; a duplicate after rebase is detectable by `ledger.py` itself (its refusal names the duplicate lines), so the detection code already exists; the renumber would be a new `ledger.py` mode or a Markdown procedure in Step 3b. No script in the repo renumbers anything today (Step 3b is pure Markdown + git commands; no test covers it).

## Security Considerations
- Authentication/Authorization: reading another user's/host's data via `bb terminal run --machine` runs commands with the bb machine's permissions (`maxPermissionMode: full` on dell-mff); the report would run only fixed `git` read commands. The trace index is read-only; the db file is the owner's.
- Data Privacy: the index holds summaries of every session's prompts and tool results (up to ~1,000 chars/event), possibly secrets. `retro` already says transcripts and digests stay in the conversation, never in the repo; the fallback inherits that rule. The harness must use fixtures, never real transcripts.
- Input Validation: index text, a ledger fetched from a remote machine, and fixture history are untrusted data (instruction-like text is a harness case). Remote output must pass through `parse_ledger` unchanged. Renumbering must touch branch-added lines only (worktree-merge failure mode 13) and never a `close` line it did not add.

## Stub-`bb` pattern (read at completion; `sdd-flow/scripts/tests/test_tier_mirror.py`, 373 lines)
- `FAKE_BB` (:14-) is a Python script written into a temp dir, made executable, and handed to the script under test through the `BB_CLI` env var; `PATH` is pinned to `/usr/bin:/bin` and every inherited `BB_*` variable is dropped (`run_script` :123-139), so the real `bb` cannot be reached.
- The stub keeps the tracker in a JSON file named by `FAKE_BB_STATE`, appends every argv (minus `--json`) to `state["calls"]`, answers with the real CLI's JSON shapes, and fails on demand (`state["fail"]` prefix match -> `{"ok": false, ...}` exit 1). Tests assert on `state()["calls"]` and the file state.
- Consequence for Tier 2: a remote-read test needs the script under test to take its `bb` path from an env var (as `tier-mirror.py` does with `BB_CLI`); `ledger.py app_section` has no such seam today. A stub for `bb terminal run` would return `{output, exitCode, truncated}` and could simulate truncation, an offline machine and a bad exit. The same stub, with the model CLI in place of `bb`, is the harness's deterministic half (as `test_second_model_review.py` already does).
