# Rare case — Mid-Phase Handoff

Read this only when a subagent returns a "needs continuation" signal, or `/sdd-flow continue` finds a `## PARTIAL: needs continuation` block latest. It is orchestrator-level and applies across all phases.

---

## Mid-Phase Handoff Protocol (automatic, inside an active flow)

Fires when a phase-execution / fix / continuation subagent trips its Reads Safety-Net and returns a "needs continuation" signal. **Distinct from Session Resumption** (the user re-invoking `/sdd-flow continue` in a fresh session). Both reuse the same artifact formats (`progress.md`, `*-compacted-*.md`); they differ only in trigger.

1. The orchestrator reads ONLY the latest compaction file path and the `## PARTIAL: needs continuation` block in `progress.md` — not the full work product.
2. It spawns a **fresh** subagent with **body `bodies/continue.md`**, **of the agent type the first spawn of that step was, with the model override the phase chapter gives that spawn**: `agent-engineering:sdd-critical-reviewer` (Opus) for the successor of a panel synthesis (3c Stage 2) or of a review on the Claude route that the phase chapter gives that type (3d, the 3e.5 check of the spec fix, the feature code review at 4b); `agent-engineering:sdd-workhorse` with the per-spawn override `opus` for the successor of a design brief (2.5a, 2.5c) or of an implementer (whole-feature 4a or a chunk of it, per-slice 4a); `agent-engineering:sdd-workhorse` for every other step that can trip. The orchestrator takes the type and the override from the phase chapter and from `phases/model-routing.md`, as it does for a first spawn — neither is written in a prompt, so neither can be read back from one — and a successor's own successor is spawned the same way. The agent type carries the step's model and its standing instructions: a critical review finished by a workhorse would be finished on Sonnet, by an agent whose own instructions tell it not to do adversarial review. An override the orchestrator added to one spawn on its own (`SKILL.md` → Model Routing, the escalation) is repeated when the handoff is made in the same session; a resumed session has no record of it and spawns as the chapter says. The successor receives: the resolved compaction file path, all resolved phase artifact paths, the Safety-Net Rule, a **fresh** counter file (`Reads: 0/15`, or `/20` for implementation), the matching compact body path, and an instruction to resume from the compaction file's "Current Focus" section. **It is also told which step it continues, and the first spawn's prompt is the rule:** everything that spawn was given is given again, stated in the successor's prompt and never left for the compaction file to carry. That is the body the first spawn ran, by path, under the name **STEP BODY**; its task text and every rule embedded in its prompt; its `MODE`, `SCOPE`, `ITER`, `BASE`, `SNAPSHOT`, and `FIXED`, where it had them; every input path; and every output it writes — its document and its progress marker among them. `bodies/continue.md` says how to pick the work up; the step's own body says what the step must still check and produce. A spawn that ran no body file — a fix, whose instructions are its task text and embedded rules — is given those again and no STEP BODY, with the step's name stated in one line (`Step: 4c fix`, `Step: SLICE-002 fix iter 2`): if the successor trips in its turn, that name is what its own `Step:` line repeats. Without this the successor of, say, the final verification (`bodies/code-review.md` with `MODE: site-verification-only`) is not told that this is the review it is finishing: it can leave out a check that mode requires, or write the wrong marker. The blind site count's handoff, below, has a closed list of its own and is the one exception. What follows spells this rule out for the tracing and evals inputs; it adds nothing to it. It also receives **the tracing inputs a first spawn of that step is given** — for a planning step, TRACING, the observability line, and (from 3c on) the gate line, as `phases/planning-inputs.md` lists them; for a Step 4 step, the gate line and, with `tracing: on`, the paths the **Tracing inputs** block of `phases/implementation-inputs.md` gives that step, with the same TRACE_TREE path the first spawn had. A successor that is not told the gate would run as if it were off. **The same holds for the evals inputs of a planning step:** the successor of a design-brief, planning, or planning-completion spawn is given the observability line and, when it says `present`, EVALS; the successor of a spec review or a spec fix (3c fix, 3d, 3e) is given the line `evals: on` or `evals: off`, EVALS when it is `on`, and — a fix — the **Evals rule for spec fixes** its first spawn carried (`phases/planning.md`). **And for a Step 4 step:** the successor is given the line `evals: on` or `evals: off` and, with the gate on, the paths the **Evals inputs** block of `phases/implementation-inputs.md` gives that step — for the successor of a review or of the fix that answers one, the same eval run line and EVAL_RESULTS path the first spawn had. No eval run of record is made for a successor: it continues a review whose run was already made.
3. The successor inherits the Safety-Net Rule and may itself bail out — the orchestrator can chain multiple handoffs within one phase.

**Review handoff.** When the step that tripped is a review step, its continuation takes the route the review was on: on the second model it is not a subagent but a new reviewer call with `bodies/continue.md` as the body, the same role file, and everything else the first call's prompt held — the review's own body as STEP BODY, its mode, scope, and iteration, its inputs and outputs, as step 2 says (`references/second-model-review.md` §6). On the Claude route it is a subagent of the review's own agent type, as step 2 says — `agent-engineering:sdd-critical-reviewer` for a critical review.
