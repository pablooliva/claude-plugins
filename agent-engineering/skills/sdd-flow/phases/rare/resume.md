# Rare case — Session Resumption · Phase Detection

Read this only on `/sdd-flow continue` (a fresh session resuming a flow). It holds the resume rule of every halt block.

---

## Session Resumption (user-triggered `/sdd-flow continue`)

The user re-invokes `/sdd-flow continue` in a fresh session; the orchestrator resumes from the most recent state in `progress.md`:

1. Read `SDD/.records/progress.md` (re-derive SKILL_ROOT from the record written at Step 0; re-resolve it if absent). If that record carries `Next-tier cycle` lines (`phases/rare/next-tier.md`), this is a next-tier cycle: take the tier, **TIER_PLAN**, and the previous tier's research document from them and pass them to every spawn exactly as a fresh run would — never derive the tier plan's path from the suffixed feature name. **Tracing is re-derived the same way, never guessed:** TRACING comes from the Step 0 record, and the observability line is the `Observability record: …` line written under the latest `## Design Brief - APPROVED` (`phases/design-gate.md` → 2.5b); the gate is the `tracing:` part of the latest `## Gates - ` line after the latest `Planning Phase - COMPLETE` (`phases/planning.md` → 3c). Every spawn a resumed session makes is passed the tracing inputs a first spawn of that step is given. **The evals gate is read from the same line:** its `evals:` part. EVALS and EVAL_TEMPLATES are derived from SKILL_ROOT, like every path inside this skill. Every Step 4 spawn a resumed session makes is passed the evals inputs a first spawn of that step is given, and **with the evals gate on, a resumed session that starts a 4b review or a 4e.5 verification from the beginning — the per-slice review, the feature code review, or the final check's verification, and no other review step — makes the eval run of record first** (`phases/implementation-inputs.md`), whether or not an `## Eval Run` line for that scope and iteration is already there: a run costs a few calls to a model, and a review must never read a run older than the code in front of it. A continuation of a review that handed off (`phases/rare/handoff.md`) is not a review started from the beginning: it keeps the run its first spawn was given.
   **The reviewer is re-read the same way:** REVIEWER is the `Reviewer: …` line of the Step 0 record, and it is not resolved again (`references/second-model-review.md` §2).
2. Determine which phase and sub-step is active (Phase Detection Priority below).
3. Resume from the exact sub-step where work was interrupted by spawning the appropriate subagent — or, for a review step on the second-model route, by running the reviewer call again from a fresh prompt file. **On the second-model route a review marker alone does not mean the review is done.** The reviewer appends its marker while it is still running, before the runner script has checked the run. So when the recorded reviewer line does not start with `claude`, a review marker of a second-model review step (`references/second-model-review.md` §1) counts only if a `## Review Route - [step-id]-[iter]: OK …` or `… claude (fallback …)` line for that step and iteration follows it. A marker with no such line belongs to a run that was cut off, or failed its check: run that review again, and read the newer marker. A `## Failed Review Run - [step-id]-[iter]: …` line says the same of the marker before it, in so many words: it is never a review result.
4. If the orchestrator's marker says a phase is done (table below), advance to the next phase.

### Phase Detection Priority

Rules are evaluated top-to-bottom; the first matching rule fires and short-circuits later rules. Detection operates ONLY on the live `progress.md` — archives under `progress-archive/` are never scanned (Progress Rotation, `phases/rare/rotation.md`, carries pending blocks forward).

**Scope: the current feature only.** Every rule below reads only the lines after the latest `## Flow Started - ` line — the Step 0 record (`phases/setup.md`). Markers above it belong to earlier features and never match, and a finished feature's `Finished:` summary line matches nothing.

**Only the orchestrator declares a phase done, and only after the phase's last step.** A completion subagent's banner says its own work is finished, never that the phase is:

| Marker | Written by | Means |
|---|---|---|
| `## Flow Started - [###]-[feature-name]` | orchestrator, Step 0 | a feature's record begins here |
| `## Research - Accepted` | orchestrator, after the 2e commit | research is done |
| `Planning Phase - COMPLETE` | completion subagent, 3a | the spec is written — reviews not yet run |
| `## Planning - Accepted` | orchestrator, on `approve` at the stop after the spec (3g) | planning is done |
| `## Feature - Implementing` (+ `Base commit:`) | orchestrator, before 4a (per-slice: before 4a.0) | implementation has begun; the commit it started from |
| `Implementation Phase - COMPLETE` | completion subagent, 4f | completion documents are written — nothing committed yet |
| `## Implementation - Committed` | orchestrator, after the 4i commit | the code is committed |
| `## Feature - Done` | orchestrator, after the 4j announcement | the feature is done |

Slice-level markers — who writes each, at which step — are in `phases/implementation-per-slice.md` → Who owns what on the slice path.

**Every stop that waits for an answer has a halt block, a rule here that resumes it, and a row in `docs/sdd-flow-diagram.md`.** Stops that need no answer write no block and say so where they are defined: the slice pause (a plain `continue` starts the next slice, found from the slice markers), and the terminal stops — decomposition, a broken install, a subagent that failed twice — which are not resumed at all.

**A latest halt block always wins.** When the latest block in the file is a `## Awaiting …` or `## PARTIAL…` block, only a halt-block rule may fire: the rule for that header, or the catch-all. The three state rules that sit among the halt rules (a drafted brief with no gate shown; a re-plan asked for and not yet drafted; a re-plan's planning run in progress) and every phase rule apply only when no halt block is latest — otherwise they would route past a halt nobody has answered.

- **`## Awaiting Clarification` block latest in `progress.md`** (the Step 1.5 gate is waiting): if `SDD/research/CLARIFICATION-[###]-[feature-name].md` now exists → resume at Step 2 (gate satisfied); if it still doesn't, ask the Step 1.5 question again. This rule sits with the other halt blocks, above the phase rules.

- **`## Awaiting Design Approval` block latest in `progress.md`** (the design gate, Step 2.5b, is waiting): re-show the gate from the brief on disk — `phases/design-gate.md` → 2.5b — and act on the reply. Nothing is re-spawned. The block's `Re-plan:` line says whether an `approve` continues into a first planning run or a re-plan.

- **The latest `## Design Brief - ` line is `Drafted`, and no `## Awaiting Design Approval` block follows it** (the brief was written or revised, and the flow stopped before the gate was shown): go to 2.5b and show the gate. This rule sits above the implementation rules on purpose — during a re-plan the implementation markers are still present, and without it `continue` would resume the old plan with an unapproved brief. A re-plan interrupted before its revise subagent wrote the `Drafted` line is the next rule's case.

- **A re-plan was asked for and its brief is not drafted yet** — a `## Re-plan Requested` line (`phases/implementation-per-slice.md` → PAUSE) with no `## Design Brief - ` line after it: run the re-plan (`phases/rare/replan.md` → Running the re-plan) with the request that line records. It sits above the implementation rules for the same reason as the rule above: without it, the slice just committed would read as "start the next slice" of the plan being replaced.

- **A re-plan's planning run is in progress** — the latest `## Awaiting Design Approval` block says `Re-plan: yes`, a `## Design Brief - APPROVED` line follows it, and no `## Planning - Accepted` line follows that: resume Step 3 (3a–3g) for the re-plan, with the slice review named in that block. Do not resume implementation — its markers belong to the plan being replaced.

- **`## Awaiting Spec Approval` block latest in `progress.md`** (the stop after the spec, Step 3g, is waiting): show the stop again, read afresh from the spec, the brief, and the PANEL-SPEC on disk — the user may have edited the spec (`phases/planning.md` → 3g) — and act on the reply. Nothing is re-spawned.

- **A `## Spec Stop Request` follows the latest `## Awaiting Spec Approval` block, and no `## Spec Stop Fix - Done` line follows the request** (the owner asked for cuts or additions at the stop after the spec, and the fix did not finish): spawn the 3g fix subagent again with the request recorded under that line, verbatim, over the spec as it was left (`phases/planning.md` → 3g); it skips what an earlier run already changed. Then carry on as the next rule says.

- **A `## Spec Stop Fix - Done` line follows the latest `## Awaiting Spec Approval` block, and no `## Planning - Accepted` line follows it** (the spec was changed at the stop after the spec, and the stop was not yet shown again): when `git status --porcelain` shows the spec changed, commit it as 3g says; then show the 3g stop again. 

- **`## Awaiting Gate Decision` block latest in `progress.md`** (3c could not decide the `tracing` gate, the `evals` gate, or both: the spec says `true` for one and the application had no tracing foundation when the design brief was approved, or a field holds a value outside `auto`, `true`, `false`; `phases/planning.md` → 3c): read the spec's `tracing:` and `evals:` fields again — the user may have edited them — and make the 3c gate decision for both. If both resolve, append the `## Gates - tracing: <on|off>, evals: <on|off>` line and carry on with 3c's panel; that line is what ends the halt. If either still does not, re-show the message for each case it is and stop with the block pending. Nothing is spawned either way before the gate resolves. This holds during a re-plan too: the block is the latest, so it is read before the re-plan rules above.

- **`## Awaiting Eval Run` block latest in `progress.md`** (evals gate on: the eval run of record ended `UNAVAILABLE` twice — the model the application calls could not be reached — so the review that was about to start was not started; `phases/implementation-inputs.md` → *The eval run of record*): make the run again for the scope and iteration the block names, and act on how it ends exactly as that procedure's step 3 says. A result, or a run that is the implementation's to repair, ends the halt: append the `## Eval Run <SCOPE> iter <k> - …` line and start that review — the 4b review of that scope or, when the block names `FEATURE` at an iteration of the final check, the 4e.5 review; the sub-step rules below say which one is owed. `UNAVAILABLE` again: re-show the block and stop with it pending. Nothing else is spawned before the run is made, and no fix round is counted for it.

- **`## Awaiting Final Check Resolution` block latest in `progress.md`** (the 4e.5 final check still had HIGH or MEDIUM findings after its two fix rounds, or completion at 4f returned items that need code or tests changed; the block's first line says which): the user has resolved findings or amended the SPEC. Resume at 4e.5 step 1 at the next unused iteration for `FEATURE` (one past the highest `## Review FEATURE iter <k>` line), with a fresh 2-round cap and no snapshots on that first iteration. **Write no new `## Final Check - Started`** — this halt block is the resumed run's boundary, and the review-loop rules below carry on from the markers written after it. Never resume from the halted iteration's review.

- **`## Awaiting Slice Resolution` block latest in `progress.md`** (a slice's fix loop hit its cap or stalled — per-slice 4c): the user has resolved findings or amended the SPEC. For the slice the block names, spawn a 4b review in full, with no snapshots, at one past the highest `## Review SLICE-XXX iter <k>` line after that slice's latest `In Progress` entry, with a fresh 2-round cap and a stall check that starts over from that review. The review-loop rules below carry on from the markers written after this block. Never resume from the halted iteration's review.

- **`## Awaiting Commit Approval` block latest in `progress.md`** (the 4h checkpoint was shown and has no "yes" yet — the session ended before an answer, or the answer was "no"): re-show the 4h checkpoint (`phases/end-of-feature.md` → 4h) — the growth check run again, since the user may have cut code — and act on the reply. Nothing is re-spawned, nothing is committed, and no sign-off or size is recorded as accepted until the answer is yes.

- **`## PARTIAL: needs continuation` block latest in `progress.md`** (a subagent tripped its Safety-Net and the session ended before its successor was spawned): run the Mid-Phase Handoff (`phases/rare/handoff.md`) for the step the block names, from the compaction file it names. The block's `Step:` line names the step's body and its `MODE`, `SCOPE`, and `ITER`; the successor is then spawned as the agent type a first spawn of that step is, and its prompt built as that spawn's is, from the phase chapter, as the handoff's step 2 says. A block with no `Step:` line was written by a compact command the user ran by hand: work the step out from where the block says the work stopped and from the sub-step rules below, and if that leaves two candidates, show the block and ask. This sits above every phase rule, so unfinished work is continued from its compaction and never mistaken for a finished step because its artifact already exists.

- **Any other `## Awaiting …` block latest in `progress.md`** (the catch-all — a halt this version has no rule for): show the block to the user verbatim, say that there is no resume rule for it, and stop. Never guess what it was waiting for, and never route past it. When the user says how to proceed, append `## Halt Resolved - <the block's header text>` with their instruction on one line, so the block is no longer latest, and evaluate these rules again.

- **A `## Design Brief - APPROVED` line follows the latest `## ADR Candidates` entry, and no `## ADR Capture - Done` line follows that entry** (the brief was approved, and the flow stopped before the accepted decision records were written): run the capture now (`phases/design-gate.md` → 2.5b, ADR candidates) for every candidate not named in an `## ADR Candidate Dropped - ` line, append `## ADR Capture - Done (…)`, and evaluate these rules again — planning (3a) follows.

- If **`## Feature - Done`** → the feature is finished and only its rotation is owed (the rotation replaces this record with the `Finished:` line): run the feature-completion rotation (4j), then show the final summary.
- If **`## Implementation - Committed`** with no `## Feature - Done` → 4j: the task mirror, the announcement, `## Feature - Done`, the rotation.
- If **"Implementation Phase - COMPLETE"** with no `## Implementation - Committed` → the completion subagent finished (4f) and nothing has been committed. For a tiered spec, run the in-review task mirror if no `## Task Mirror - ` line follows the `COMPLETE` line (it is safe to repeat), then go to **4h** — which runs the growth check and stops when a sign-off is asked for or the feature is over its growth budget — unless a `## Sign-off - ` or `## Growth - ` line already follows the latest `Implementation Phase - COMPLETE`: a resumed session never commits past an acceptance nobody gave. Those lines mean the user said yes at 4h and the session ended before the commit: go to **4i**. This line alone never means done.
- If implementation is active → resume the appropriate sub-step (4a–4f or the per-slice cycle). The `BASE` for the feature code review (4b) and for 4e.5, in both delivery modes, is the `Base commit:` under `## Feature - Implementing`. When that line is absent and no Step 4 marker exists either (no `## Feature - Implemented`, no `## Slice … - ` line, no review marker), implementation has not started: write the line and begin 4a (per-slice: 4a.0). **Per-slice cycle sub-steps** are resolved for the **current slice** — the one named by the latest `## Slice SLICE-XXX - In Progress` entry. **Only slice markers after the latest `## Planning - Accepted` line count**: a re-plan writes a second `Accepted` line, and the slice markers above it belong to the plan it replaced. The first that applies:
  - No slice marker → per-slice 4a.0 — after a re-plan with no later `## Slices Superseded` line, its re-plan preparation comes before the table check, picking up from a `## Re-plan Preparation - Started` line if one is there — then 4a for the first row that is not `Complete`.
  - `In Progress` with no `Implemented` → 4a was interrupted: re-spawn it with `--resume SLICE-XXX`.
  - `Implemented`, and the slice's latest review marker is absent or `REJECTED` → the review-loop sub-steps below (review, fix, and the fix-loop halt).
  - The slice's latest review is `APPROVED`, with no `Committed` → 4c.6.
  - `Committed` → 4a for the next row after that slice, in table order, that is not `Complete` (with `--resume` if the row is already `In Progress` — a 4a cut short before its first progress entry); none → the end-of-feature cycle: the feature code review (4b) and its fix (4c), then 4e.5, by the rules below.

  **Review-loop sub-steps** are resolved from these literal lines, for the active scope (`SLICE-XXX` = the current slice above, until its `Committed` line; `FEATURE` otherwise — the feature code review (4b) and 4e.5, in both delivery modes), taking the highest iteration `N` present. **Only markers after the scope's anchor count** — the latest `## Slice SLICE-XXX - In Progress` for a slice, the latest `## Feature - Implemented` (per-slice: the last slice's `Committed` line) for the feature code review, the latest `## Final Check - Started` for 4e.5 — so a re-run (a slice re-attached with `--resume`; a re-planned slice that reuses an ID) never matches a discarded cycle's markers. (A 4e.5 resumed from `## Awaiting Final Check Resolution` writes no new anchor; a slice resumed from `## Awaiting Slice Resolution` writes none either: that block is the boundary for the cap and for the stall check.) With `evals: on`, the eval run of record is made before any review a session starts from the beginning. Evaluate in this order:
  - `## Slice SLICE-XXX - Implemented` or `## Feature - Implemented` (per-slice: the last slice's `Committed` line) with no review marker after it → spawn the 4b review at iteration 0. `## Final Check - Started` with no review marker after it → 4e.5 at `k = 1`.
  - `## Final Check - Complete` after the latest `## Final Check - Started` → 4e.5 is done; resume at 4f or later by the existing sub-step detection. **One exception:** an `## Awaiting Final Check Resolution` block that follows that `Complete` line re-opened the final check (4f returned items that need code or tests changed) — then only a `Complete` line written after that block closes 4e.5.
  - `## Fix <SCOPE> iter <k> - Complete` with no `## Review <SCOPE> iter <k> - …` → spawn the review at iteration k (per-slice 4b; 4e.5 step 2), first taking the iteration's *after fix* snapshot again when a usable *before fix* one follows the scope's boundary, and passing `SNAPSHOT`, `FIXED`, and `PREVIOUS REVIEW`; with no usable pair, none of them (`phases/implementation-per-slice.md` → 4c, *The snapshots*).
  - In 4e.5, `## Review FEATURE iter <N> - APPROVED` with no `## Final Check - Complete` after it → the loop ended and the session stopped before its closing anchor: append `## Final Check - Complete` and go to 4f.
  - `## Review <SCOPE> iter <N> - REJECTED` with no `## Fix <SCOPE> iter <N+1> - Complete` → unless the cap (or, for a slice, the stall rule) is already met — then apply that step's halt — spawn the fix subagent for iteration N+1 (per-slice 4c / 4e.5 step 3 — never the feature code review's 4c, see the exception below), first taking its *before fix* snapshot unless a `## Snapshot <SCOPE> iter <N+1> - …` line already follows the scope's boundary: a fix spawned again keeps the snapshot of its first attempt.
  - **Feature code review exception (both delivery modes):** after `## Review FEATURE iter 0 - …`, resume 4c by the existing sub-step detection (4c writes no `## Fix` marker); the rules above apply again once `## Final Check - Started` is present.
  - Caps count the `## Fix <SCOPE> iter <k>` lines already present (for 4e.5, only those after the latest `## Final Check - Started` or the latest `## Awaiting Final Check Resolution` after it; for a slice, only those after its latest `In Progress` entry and, when one follows that entry, its latest `## Awaiting Slice Resolution`), so a resumed run never resets a cap — only the user's answer to a halt does.
- If **"Planning Phase - COMPLETE"** with a later `## Planning - Accepted` line → start Step 4 (route on `delivery_mode:`).
- If planning is active — including `Planning Phase - COMPLETE` with no later `## Planning - Accepted`, since the completion subagent writes `COMPLETE` in 3a, before the reviews → resume the appropriate sub-step (3a–3g). After a `### Panel Review Halt`, that is a fresh 3c panel run over the spec as the user left it. After a `### Spec Fix Check Halt`, it is a fresh 3e.5 check over the spec as the user left it (with its one further fix still available). Within 3e.5, a `## Spec Fix Check - ` line that is the latest planning line says where the check stands — the orchestrator writes it only after the run's `## Review Route` line (second-model route) or the subagent's return (Claude route), so it counts as it stands, and the ordering rule of step 3 above (a reviewer's own marker counts only with a later `## Review Route` line) does not apply to it: `CONFIRMED` → 3f; one `OPEN` → the further fix, then the check; a second `OPEN` with no halt line → write the halt. 3c begins with the gate decision (`tracing` and `evals`) whenever no `## Gates - ` line follows the latest `Planning Phase - COMPLETE` (`phases/planning.md` → 3c). 3g is never skipped: its deviation check runs before `## Planning - Accepted` is written.
- If **`## Research - Accepted`** → Step 2.5 (`phases/design-gate.md`), by the **latest** `## Design Brief - ` line in `progress.md`: no such line → 2.5a (a brief file with no `Drafted` line is a partial write — the subagent overwrites it); latest is `Drafted` → 2.5b (show the gate); latest is `APPROVED` → start Step 3 (planning). Read the latest line, never "any": a re-plan writes a new `Drafted` line below an old `APPROVED` one.
- If research is active — a Step 0 record with none of the markers above → resume 2a, 2b, or 2e from what is on disk. The first that applies:
  - no CLARIFICATION file and no `## Clarification Skipped` block → Step 1.5 (`phases/setup.md`);
  - no RESEARCH document → 2a;
  - RESEARCH document, but no "Research phase complete" note from the completion subagent → 2a's completion spawn;
  - no `## ADR Candidates` entry for this feature → 2b; re-running it is safe (it writes no record, and the body declines a decision that already has one);
  - otherwise → 2e: commit, then `## Research - Accepted`.
- If no phase info → nothing to resume. When the latest record is a `Finished:` line, tell the user that feature is done and show the line. Otherwise start from Step 0 (read `phases/setup.md`).
