# Protocols — Mid-Phase Handoff · Session Resumption · Phase Detection · Errors

Read this when handling `/sdd-flow continue`, when a subagent returns a "needs continuation" signal, or on any error. These protocols are orchestrator-level and apply across all phases.

---

## Mid-Phase Handoff Protocol (automatic, inside an active flow)

Fires when a phase-execution / fix / continuation subagent trips its Reads Safety-Net and returns a "needs continuation" signal. **Distinct from Session Resumption** (the user re-invoking `/sdd-flow continue` in a fresh session). Both reuse the same artifact formats (`progress.md`, `*-compacted-*.md`); they differ only in trigger.

1. The orchestrator reads ONLY the latest compaction file path and the `## PARTIAL: needs continuation` block in `progress.md` — not the full work product.
2. It spawns a **fresh** subagent with **body `bodies/continue.md`**, **of the agent type the first spawn of that step was, with the model override the phase chapter gives that spawn**: `agent-engineering:sdd-critical-reviewer` (Opus) for the successor of a panel synthesis (3c Stage 2) or of a critical review on the Claude route (2c, 3d, the 3e.5 check of the spec fix, 4d); `agent-engineering:sdd-workhorse` with the per-spawn override `opus` for the successor of a design brief (2.5a, 2.5c); `agent-engineering:sdd-workhorse` for every other step that can trip. The orchestrator takes the type and the override from the phase chapter and from `SKILL.md` → Model Routing, as it does for a first spawn — neither is written in a prompt, so neither can be read back from one — and a successor's own successor is spawned the same way. The agent type carries the step's model and its standing instructions: a critical review finished by a workhorse would be finished on Sonnet, by an agent whose own instructions tell it not to do adversarial review. An override the orchestrator added to one spawn on its own (`SKILL.md` → Model Routing, the escalation) is repeated when the handoff is made in the same session; a resumed session has no record of it and spawns as the chapter says. The successor receives: the resolved compaction file path, all resolved phase artifact paths, the Safety-Net Rule, a **fresh** counter file (`Reads: 0/15`, or `/20` for implementation), the matching compact body path, and an instruction to resume from the compaction file's "Current Focus" section. **It is also told which step it continues, and the first spawn's prompt is the rule:** everything that spawn was given is given again, stated in the successor's prompt and never left for the compaction file to carry. That is the body the first spawn ran, by path, under the name **STEP BODY**; its task text and every rule embedded in its prompt; its `MODE`, `SCOPE`, `ITER`, `BASE`, `SNAPSHOT`, and `FIXED`, where it had them; every input path; and every output it writes — its document and its progress marker among them. `bodies/continue.md` says how to pick the work up; the step's own body says what the step must still check and produce. A spawn that ran no body file — a fix, whose instructions are its task text and embedded rules — is given those again and no STEP BODY, with the step's name stated in one line (`Step: 4c fix`, `Step: SLICE-002 fix iter 2`): if the successor trips in its turn, that name is what its own `Step:` line repeats. Without this the successor of, say, the final verification (`bodies/code-review.md` with `MODE: site-verification-only`) is not told that this is the review it is finishing: it can leave out a check that mode requires, or write the wrong marker. The blind site count's handoff, below, has a closed list of its own and is the one exception. What follows spells this rule out for the tracing and evals inputs; it adds nothing to it. It also receives **the tracing inputs a first spawn of that step is given** — for a planning step, TRACING, the observability line, and (from 3c on) the gate line, as `phases/planning.md` lists them; for a Step 4 step, the gate line and, with `tracing: on`, the paths the **Tracing inputs** block at the top of `phases/implementation-whole-feature.md` gives that step, with the same TRACE_TREE path the first spawn had. A successor that is not told the gate would run as if it were off. **The same holds for the evals inputs of a planning step:** the successor of a design-brief, planning, or planning-completion spawn is given the observability line and, when it says `present`, EVALS; the successor of a spec review or a spec fix (3c fix, 3d, 3e) is given the line `evals: on` or `evals: off`, EVALS when it is `on`, and — a fix — the **Evals rule for spec fixes** its first spawn carried (`phases/planning.md`). **And for a Step 4 step:** the successor is given the line `evals: on` or `evals: off` and, with the gate on, the paths the **Evals inputs** block at the top of `phases/implementation-whole-feature.md` gives that step — for the successor of a review or of the fix that answers one, the same eval run line and EVAL_RESULTS path the first spawn had. No eval run of record is made for a successor: it continues a review whose run was already made.
3. The successor inherits the Safety-Net Rule and may itself bail out — the orchestrator can chain multiple handoffs within one phase.

**Review handoff.** When the step that tripped is a review step, its continuation takes the route the review was on: on the second model it is not a subagent but a new reviewer call with `bodies/continue.md` as the body, the same role file, and everything else the first call's prompt held — the review's own body as STEP BODY, its mode, scope, and iteration, its inputs and outputs, as step 2 says (`references/second-model-review.md` §6). On the Claude route it is a subagent of the review's own agent type, as step 2 says — `agent-engineering:sdd-critical-reviewer` for a critical review.

## Progress Rotation (orchestrator-only)

`progress.md` is append-only **within a generation**; rotation starts a new generation. Only the orchestrator rotates, only between spawns (never mid-subagent).

**Triggers:** (a) feature completion — Step 4j / per-slice end-of-feature 4j; (b) the live file exceeds ~500 lines at a phase-boundary commit (2e, 3f, 4i, per-slice 4c.6) or during an interactive compact/continue.

**Procedure:**
1. Create `SDD/orchestration/progress-archive/` if absent. Move the verbose history to `progress-archive/progress-[SPEC-### or scope]-[YYYY-MM-DD_HH-MM-SS].md` — feature-completion rotation moves that feature's full history; size rotation moves all *resolved* blocks, **including — within the still-active feature — blocks of phases the orchestrator has marked done** (`## Research - Accepted`, `## Planning - Accepted`: e.g., the research and planning history of a feature still in implementation). Blocks of the currently active phase always stay live.
2. Rewrite the live `progress.md` head as a bounded `## Current State`: canonical identifiers, SKILL_ROOT, flags, artifact pointers, and "History archived to <path>". Below it:
   - **A finished feature is one line** of the form `Finished: SPEC-[###] [feature-name] — <outcome>; history: <archive path>` — plain text with no `## ` header and none of the marker strings below, so no phase rule can ever match it.
   - **The active feature keeps its Step 0 record** (the `## Flow Started - ` line and the lines under it) and, after it, its canonical phase-state lines **verbatim and in their original order**: `## Research - Accepted`, every `## Design Brief - ` line and the `Observability record: …` line under each `APPROVED` one, every `## Re-plan Requested` line, `## ADR Candidates` / `## ADR Candidate Dropped - ` / `## ADR Capture - Done`, `Planning Phase - COMPLETE`, every `## Gates - ` line (the latest one after the latest `Planning Phase - COMPLETE` holds the tracing gate and the evals gate every later spawn is passed), `## Planning - Accepted` (each one — a re-plan writes a second, and the slice rules read only what follows the latest), `## Feature - Implementing` with its `Base commit:` line, `Implementation Phase - COMPLETE`, `## Implementation - Committed`. Phase Detection (below) matches these literal markers, not paraphrases, and reads only what follows the latest `## Flow Started - ` line.
3. **Carry forward verbatim, as the latest blocks, every pending halt block.** A pending halt block is ANY block whose header starts with `## Awaiting ` or `## PARTIAL` — match the prefix, not a fixed list; real files contain custom halt headers. (Canonical forms: `## Awaiting Clarification`, `## Awaiting Design Approval`, `## Awaiting Spec Approval`, `## Awaiting Gate Decision`, `## Awaiting Eval Run`, `## Awaiting Slice Resolution`, `## Awaiting Final Check Resolution`, `## Awaiting Commit Approval`, `## PARTIAL: needs continuation`.) Carry anything Phase Detection or the Mid-Phase Handoff protocol still needs. Resolved blocks are archived; pending ones never are.
4. Append a `### Progress rotated ([YYYY-MM-DD_HH-MM-SS])` line recording the archive path.

**Invariants:** Everything that remains in the live file is preserved **byte-identical** — moved or kept by mechanical operations, never retyped, reflowed, re-encoded, or summarized; the ONLY newly written text in a rotation is the `## Current State` head, a finished feature's `Finished:` line, and the `### Progress rotated` stamp. Phase Detection (below) operates ONLY on the live `progress.md`; archives are never scanned. Pending blocks survive every rotation. The audit trail is preserved in the archive files and in git history (phase-boundary commits include `progress.md`).

**Not a rotation: setting a file aside.** `/adhoc-compact` can move the whole `progress.md` — pending blocks included — to `progress-archive/` and start a fresh one, when the user says the work in it is finished or abandoned (`commands/adhoc-compact.md` → step 3). It warns first when the file holds an unfinished feature and needs an explicit yes, because the feature stops being resumable until the file is moved back. That is a user's deliberate abandonment, outside the invariants above; the orchestrator never does it, and no rotation ever archives a pending block.

## Session Resumption (user-triggered `/sdd-flow continue`)

The user re-invokes `/sdd-flow continue` in a fresh session; the orchestrator resumes from the most recent state in `progress.md`:

1. Read `SDD/orchestration/progress.md` (re-derive SKILL_ROOT from the record written at Step 0; re-resolve it if absent). If that record carries `Next-tier cycle` lines (`phases/setup.md` → Starting the next tier), this is a next-tier cycle: take the tier, **TIER_PLAN**, and the previous tier's research document from them and pass them to every spawn exactly as a fresh run would — never derive the tier plan's path from the suffixed feature name. **Tracing is re-derived the same way, never guessed:** TRACING comes from the Step 0 record, and the observability line is the `Observability record: …` line written under the latest `## Design Brief - APPROVED` (`phases/planning.md` → 2.5b); the gate is the `tracing:` part of the latest `## Gates - ` line after the latest `Planning Phase - COMPLETE` (`phases/planning.md` → 3c). Every spawn a resumed session makes is passed the tracing inputs a first spawn of that step is given. **The evals gate is read from the same line:** its `evals:` part. EVALS and EVAL_TEMPLATES are derived from SKILL_ROOT, like every path inside this skill. Every Step 4 spawn a resumed session makes is passed the evals inputs a first spawn of that step is given, and **with the evals gate on, a resumed session that starts a 4b review or a 4e.5 verification from the beginning — the per-slice review, the whole-feature code review, or the final check's verification, and no other review step — makes the eval run of record first** (`phases/implementation-whole-feature.md`, top), whether or not an `## Eval Run` line for that scope and iteration is already there: a run costs a few calls to a model, and a review must never read a run older than the code in front of it. A continuation of a review that handed off (Mid-Phase Handoff, above) is not a review started from the beginning: it keeps the run its first spawn was given.
   **The reviewer is re-read the same way:** REVIEWER is the `Reviewer: …` line of the Step 0 record, and it is not resolved again (`references/second-model-review.md` §2).
2. Determine which phase and sub-step is active (Phase Detection Priority below).
3. Resume from the exact sub-step where work was interrupted by spawning the appropriate subagent — or, for a review step on the second-model route, by running the reviewer call again from a fresh prompt file. **On the second-model route a review marker alone does not mean the review is done.** The reviewer appends its marker while it is still running, before the runner script has checked the run. So when the recorded reviewer line does not start with `claude`, a review marker of a second-model review step (`references/second-model-review.md` §1) counts only if a `## Review Route - [step-id]-[iter]: OK …` or `… claude (fallback …)` line for that step and iteration follows it. A marker with no such line belongs to a run that was cut off, or failed its check: run that review again, and read the newer marker. A `## Failed Review Run - [step-id]-[iter]: …` line says the same of the marker before it, in so many words: it is never a review result.
4. If the orchestrator's marker says a phase is done (table below), advance to the next phase.

### Phase Detection Priority

Rules are evaluated top-to-bottom; the first matching rule fires and short-circuits later rules. Detection operates ONLY on the live `progress.md` — archives under `progress-archive/` are never scanned (Progress Rotation above carries pending blocks forward).

**Scope: the current feature only.** Every rule below reads only the lines after the latest `## Flow Started - ` line — the Step 0 record (`phases/setup.md`). Markers above it belong to earlier features and never match, and a finished feature's `Finished:` summary line matches nothing.

**Only the orchestrator declares a phase done, and only after the phase's last step.** A completion subagent's banner says its own work is finished, never that the phase is:

| Marker | Written by | Means |
|---|---|---|
| `## Flow Started - [###]-[feature-name]` | orchestrator, Step 0 | a feature's record begins here |
| `## Research - Accepted` | orchestrator, after the 2e commit | research is done |
| `Planning Phase - COMPLETE` | completion subagent, 3a | the spec is written — reviews not yet run |
| `## Planning - Accepted` | orchestrator, on `approve` at the stop after the spec (3g) | planning is done |
| `## Feature - Implementing` (+ `Base commit:`) | orchestrator, before 4a (per-slice: before 4a.0) | implementation has begun; the commit it started from |
| `Implementation Phase - COMPLETE` | completion subagent, 4f | completion documents are written — nothing committed yet |
| `## Implementation - Committed` | orchestrator, after the 4i commit | the code is committed |
| `## Feature - Done` | orchestrator, after the 4j announcement | the feature is done |

Slice-level markers — who writes each, at which step — are in `phases/implementation-per-slice.md` → Who owns what on the slice path.

**Every stop that waits for an answer has a halt block, a rule here that resumes it, and a row in `docs/sdd-flow-diagram.md`.** Stops that need no answer write no block and say so where they are defined: the slice pause (a plain `continue` starts the next slice, found from the slice markers), and the terminal stops — decomposition, a broken install, a subagent that failed twice — which are not resumed at all.

**A latest halt block always wins.** When the latest block in the file is a `## Awaiting …` or `## PARTIAL…` block, only a halt-block rule may fire: the rule for that header, or the catch-all. The three state rules that sit among the halt rules (a drafted brief with no gate shown; a re-plan asked for and not yet drafted; a re-plan's planning run in progress) and every phase rule apply only when no halt block is latest — otherwise they would route past a halt nobody has answered.

- **`## Awaiting Clarification` block latest in `progress.md`** (the Step 1.5 gate is waiting): if `SDD/research/CLARIFICATION-[###]-[feature-name].md` now exists → resume at Step 2 (gate satisfied); if it still doesn't, ask the Step 1.5 question again. This rule sits with the other halt blocks, above the phase rules.

- **`## Awaiting Design Approval` block latest in `progress.md`** (the design gate, Step 2.5b, is waiting): re-show the gate from the brief on disk — `phases/planning.md` → 2.5b — and act on the reply. Nothing is re-spawned. The block's `Re-plan:` line says whether an `approve` continues into a first planning run or a re-plan.

- **The latest `## Design Brief - ` line is `Drafted`, and no `## Awaiting Design Approval` block follows it** (the brief was written or revised, and the flow stopped before the gate was shown): go to 2.5b and show the gate. This rule sits above the implementation rules on purpose — during a re-plan the implementation markers are still present, and without it `continue` would resume the old plan with an unapproved brief. A re-plan interrupted before its revise subagent wrote the `Drafted` line is the next rule's case.

- **A re-plan was asked for and its brief is not drafted yet** — a `## Re-plan Requested` line (`phases/implementation-per-slice.md` → PAUSE) with no `## Design Brief - ` line after it: run Step 2.5's Re-plan (`phases/planning.md`) with the request that line records. It sits above the implementation rules for the same reason as the rule above: without it, the slice just committed would read as "start the next slice" of the plan being replaced.

- **A re-plan's planning run is in progress** — the latest `## Awaiting Design Approval` block says `Re-plan: yes`, a `## Design Brief - APPROVED` line follows it, and no `## Planning - Accepted` line follows that: resume Step 3 (3a–3g) for the re-plan, with the rolling ledger and the retrospective named in that block. Do not resume implementation — its markers belong to the plan being replaced.

- **`## Awaiting Spec Approval` block latest in `progress.md`** (the stop after the spec, Step 3g, is waiting): show the stop again, read afresh from the spec, the brief, and the PANEL-SPEC on disk — the user may have edited the spec (`phases/planning.md` → 3g) — and act on the reply. Nothing is re-spawned.

- **A `## Spec Stop Request` follows the latest `## Awaiting Spec Approval` block, and no `## Spec Stop Fix - Done` line follows the request** (the owner asked for cuts or additions at the stop after the spec, and the fix did not finish): spawn the 3g fix subagent again with the request recorded under that line, verbatim, over the spec as it was left (`phases/planning.md` → 3g); it skips what an earlier run already changed. Then carry on as the next rule says.

- **A `## Spec Stop Fix - Done` line follows the latest `## Awaiting Spec Approval` block, and no `## Planning - Accepted` line follows it** (the spec was changed at the stop after the spec, and the stop was not yet shown again): when `git status --porcelain` shows the spec or the PANEL-SPEC changed, commit them as 3g says; then show the 3g stop again. 

- **`## Awaiting Gate Decision` block latest in `progress.md`** (3c could not decide the `tracing` gate, the `evals` gate, or both: the spec says `true` for one and the application had no tracing foundation when the design brief was approved, or a field holds a value outside `auto`, `true`, `false`; `phases/planning.md` → 3c): read the spec's `tracing:` and `evals:` fields again — the user may have edited them — and make the 3c gate decision for both. If both resolve, append the `## Gates - tracing: <on|off>, evals: <on|off>` line and carry on with 3c's panel; that line is what ends the halt. If either still does not, re-show the message for each case it is and stop with the block pending. Nothing is spawned either way before the gate resolves. This holds during a re-plan too: the block is the latest, so it is read before the re-plan rules above.

- **`## Awaiting Eval Run` block latest in `progress.md`** (evals gate on: the eval run of record ended `UNAVAILABLE` twice — the model the application calls could not be reached — so the review that was about to start was not started; `phases/implementation-whole-feature.md` → *The eval run of record*): make the run again for the scope and iteration the block names, and act on how it ends exactly as that procedure's step 3 says. A result, or a run that is the implementation's to repair, ends the halt: append the `## Eval Run <SCOPE> iter <k> - …` line and start that review — the 4b review of that scope or, when the block names `FEATURE` at an iteration of the final check, the 4e.5 review; the sub-step rules below say which one is owed. `UNAVAILABLE` again: re-show the block and stop with it pending. Nothing else is spawned before the run is made, and no fix round is counted for it.

- **`## Awaiting Final Check Resolution` block latest in `progress.md`** (the 4e.5 final check still had HIGH or MEDIUM findings after its two fix rounds, or completion at 4f returned items that need code or tests changed; the block's first line says which): the user has resolved findings or amended the SPEC. Resume at 4e.5 step 1 at the next unused iteration for `FEATURE` (one past the highest `## Review FEATURE iter <k>` line), with a fresh 2-round cap and no snapshots on that first iteration. **Write no new `## Final Check - Started`** — this halt block is the resumed run's boundary, and the review-loop rules below carry on from the markers written after it. Never resume from the halted iteration's review.

- **`## Awaiting Slice Resolution` block latest in `progress.md`** (a slice's fix loop hit its cap or stalled — per-slice 4c): the user has resolved findings or amended the SPEC. For the slice the block names, spawn a 4b review in full, with no snapshots, at one past the highest `## Review SLICE-XXX iter <k>` line after that slice's latest `In Progress` entry, with a fresh 3-round cap and a stall check that starts over from that review. The review-loop rules below carry on from the markers written after this block. Never resume from the halted iteration's review.

- **`## Awaiting Commit Approval` block latest in `progress.md`** (the 4h checkpoint was shown and has no "yes" yet — the session ended before an answer, or the answer was "no"): re-show the 4h checkpoint (`phases/implementation-whole-feature.md` → 4h) — the growth check run again, since the user may have cut code — and act on the reply. Nothing is re-spawned, nothing is committed, and no sign-off or size is recorded as accepted until the answer is yes.

- **`## PARTIAL: needs continuation` block latest in `progress.md`** (a subagent tripped its Safety-Net and the session ended before its successor was spawned): run the Mid-Phase Handoff (above) for the step the block names, from the compaction file it names. The block's `Step:` line names the step's body and its `MODE`, `SCOPE`, and `ITER`; the successor is then spawned as the agent type a first spawn of that step is, and its prompt built as that spawn's is, from the phase chapter, as the handoff's step 2 says. A block with no `Step:` line was written by a compact command the user ran by hand: work the step out from where the block says the work stopped and from the sub-step rules below, and if that leaves two candidates, show the block and ask. This sits above every phase rule, so unfinished work is continued from its compaction and never mistaken for a finished step because its artifact already exists.

- **Any other `## Awaiting …` block latest in `progress.md`** (the catch-all — a halt this version has no rule for): show the block to the user verbatim, say that there is no resume rule for it, and stop. Never guess what it was waiting for, and never route past it. When the user says how to proceed, append `## Halt Resolved - <the block's header text>` with their instruction on one line, so the block is no longer latest, and evaluate these rules again.

- **A `## Design Brief - APPROVED` line follows the latest `## ADR Candidates` entry, and no `## ADR Capture - Done` line follows that entry** (the brief was approved, and the flow stopped before the accepted decision records were written): run the capture now (`phases/planning.md` → 2.5b, ADR candidates) for every candidate not named in an `## ADR Candidate Dropped - ` line, append `## ADR Capture - Done (…)`, and evaluate these rules again — planning (3a) follows.

- If **`## Feature - Done`** → the feature is finished and only its rotation is owed (the rotation replaces this record with the `Finished:` line): run the feature-completion rotation (4j), then show the final summary.
- If **`## Implementation - Committed`** with no `## Feature - Done` → 4j: the task mirror, the announcement, `## Feature - Done`, the rotation.
- If **"Implementation Phase - COMPLETE"** with no `## Implementation - Committed` → the completion subagent finished (4f) and nothing has been committed. For a tiered spec, run the in-review task mirror if no `## Task Mirror - ` line follows the `COMPLETE` line (it is safe to repeat), then go to **4h** — which runs the growth check and stops when a sign-off is asked for or the feature is over its growth budget — unless a `## Sign-off - ` or `## Growth - ` line already follows the latest `Implementation Phase - COMPLETE`: a resumed session never commits past an acceptance nobody gave. Those lines mean the user said yes at 4h and the session ended before the commit: go to **4i**. This line alone never means done.
- If implementation is active → resume the appropriate sub-step (4a–4f or the per-slice cycle). The `BASE` for whole-feature 4b and 4d, and for 4e.5 in both delivery modes, is the `Base commit:` under `## Feature - Implementing`. When that line is absent and no Step 4 marker exists either (no `## Feature - Implemented`, no `## Slice … - ` line, no review marker), implementation has not started: write the line and begin 4a (per-slice: 4a.0). **Per-slice cycle sub-steps** are resolved for the **current slice** — the one named by the latest `## Slice SLICE-XXX - In Progress` entry. **Only slice markers after the latest `## Planning - Accepted` line count**: a re-plan writes a second `Accepted` line, and the slice markers above it belong to the plan it replaced. The first that applies:
  - No slice marker → per-slice 4a.0 — after a re-plan with no later `## Slices Superseded` line, its re-plan preparation comes before the table check, picking up from a `## Re-plan Preparation - Started` line if one is there — then 4a for the first row that is not `Complete`.
  - `In Progress` with no `Implemented` → 4a was interrupted: re-spawn it with `--resume SLICE-XXX`.
  - `Implemented`, and the slice's latest review marker is absent or `REJECTED` → the review-loop sub-steps below (review, fix, and the fix-loop halt).
  - The slice's latest review is `APPROVED`, and there is no `Retrospective Complete` → 4c.5. If a `RETROSPECTIVE-SLICE-XXX-*` file for the slice already exists outside `superseded/` (the run ended after the retrospective was written and before its ledger, table, and progress updates), the file is the record and is kept: spawn the retrospective body with `--reconcile-ledger SLICE-XXX` and the line `FINISH: SLICE-XXX`, with 4c.5's usual inputs. It completes the missing writes from that file, ending with `Retrospective Complete`, and never writes a second retrospective.
  - `Retrospective Complete` with no later `Retro Matched` → run the Stage 1 matcher on the retrospective file that entry names, and append `Retro Matched`. Never go to the commit without it.
  - `Retro Matched` with no `Committed` → 4c.6.
  - `Committed` → 4a for the next row after that slice, in table order, that is not `Complete` (with `--resume` if the row is already `In Progress` — a 4a cut short before its first progress entry); none → the end-of-feature cycle (4d and 4e by the existing sub-step detection, 4e.5 by the rules below).

  **Review-loop sub-steps** are resolved from these literal lines, for the active scope (`SLICE-XXX` = the current slice above, until its `Retrospective Complete`; `FEATURE` otherwise — whole-feature 4b, and 4e.5 in both delivery modes), taking the highest iteration `N` present. **Only markers after the scope's anchor count** — the latest `## Slice SLICE-XXX - In Progress` for a slice, the latest `## Feature - Implemented` for whole-feature 4b, the latest `## Final Check - Started` for 4e.5 — so a re-run (a slice re-attached with `--resume`; a re-planned slice that reuses an ID) never matches a discarded cycle's markers. (A 4e.5 resumed from `## Awaiting Final Check Resolution` writes no new anchor; a slice resumed from `## Awaiting Slice Resolution` writes none either: that block is the boundary for the cap and for the stall check.) With `evals: on`, the eval run of record is made before any review a session starts from the beginning. Evaluate in this order:
  - `## Slice SLICE-XXX - Implemented` or `## Feature - Implemented` with no review marker after it → spawn the 4b review at iteration 0. `## Final Check - Started` with no review marker after it → 4e.5 at `k = 1`.
  - `## Final Check - Complete` after the latest `## Final Check - Started` → 4e.5 is done; resume at 4f or later by the existing sub-step detection. **One exception:** an `## Awaiting Final Check Resolution` block that follows that `Complete` line re-opened the final check (4f returned items that need code or tests changed) — then only a `Complete` line written after that block closes 4e.5.
  - `## Fix <SCOPE> iter <k> - Complete` with no `## Review <SCOPE> iter <k> - …` → spawn the review at iteration k (per-slice 4b; 4e.5 step 2), first taking the iteration's *after fix* snapshot again when a usable *before fix* one follows the scope's boundary, and passing `SNAPSHOT`, `FIXED`, and `PREVIOUS REVIEW`; with no usable pair, none of them (`phases/implementation-per-slice.md` → 4c, *The snapshots*).
  - In 4e.5, `## Review FEATURE iter <N> - APPROVED` with no `## Final Check - Complete` after it → the loop ended and the session stopped before its closing anchor: append `## Final Check - Complete` and go to 4f.
  - `## Review <SCOPE> iter <N> - REJECTED` with no `## Fix <SCOPE> iter <N+1> - Complete` → unless the cap (or, for a slice, the stall rule) is already met — then apply that step's halt (for a slice: if a `## Slice SLICE-XXX - Halt Note Recorded` entry already follows that review, the ledger note is written — go straight to the halt block) — spawn the fix subagent for iteration N+1 (per-slice 4c / 4e.5 step 3 — never whole-feature 4c, see the exception below), first taking its *before fix* snapshot unless a `## Snapshot <SCOPE> iter <N+1> - …` line already follows the scope's boundary: a fix spawned again keeps the snapshot of its first attempt.
  - **Whole-feature exception:** after `## Review FEATURE iter 0 - …`, resume 4c–4e by the existing sub-step detection (4c writes no `## Fix` marker); the rules above apply again once `## Final Check - Started` is present.
  - Caps count the `## Fix <SCOPE> iter <k>` lines already present (for 4e.5, only those after the latest `## Final Check - Started` or the latest `## Awaiting Final Check Resolution` after it; for a slice, only those after its latest `In Progress` entry and, when one follows that entry, its latest `## Awaiting Slice Resolution`), so a resumed run never resets a cap — only the user's answer to a halt does.
- If **"Planning Phase - COMPLETE"** with a later `## Planning - Accepted` line → start Step 4 (route on `delivery_mode:`).
- If planning is active — including `Planning Phase - COMPLETE` with no later `## Planning - Accepted`, since the completion subagent writes `COMPLETE` in 3a, before the reviews → resume the appropriate sub-step (3a–3g). After a `### Panel Review Halt`, that is a fresh 3c panel run over the spec as the user left it. After a `### Spec Fix Check Halt`, it is a fresh 3e.5 check over the spec as the user left it (with its one further fix still available). Within 3e.5, a `## Spec Fix Check - ` line that is the latest planning line says where the check stands — the orchestrator writes it only after the run's `## Review Route` line (second-model route) or the subagent's return (Claude route), so it counts as it stands, and the ordering rule of step 3 above (a reviewer's own marker counts only with a later `## Review Route` line) does not apply to it: `CONFIRMED` → 3f; one `OPEN` → the further fix, then the check; a second `OPEN` with no halt line → write the halt. 3c begins with the gate decision (`tracing` and `evals`) whenever no `## Gates - ` line follows the latest `Planning Phase - COMPLETE` (`phases/planning.md` → 3c). 3g is never skipped: its deviation check runs before `## Planning - Accepted` is written.
- If **`## Research - Accepted`** → Step 2.5 (`phases/planning.md`), by the **latest** `## Design Brief - ` line in `progress.md`: no such line → 2.5a (a brief file with no `Drafted` line is a partial write — the subagent overwrites it); latest is `Drafted` → 2.5b (show the gate); latest is `APPROVED` → start Step 3 (planning). Read the latest line, never "any": a re-plan writes a new `Drafted` line below an old `APPROVED` one.
- If research is active — a Step 0 record with none of the markers above → resume 2a–2e from what is on disk. The first that applies:
  - no CLARIFICATION file and no `## Clarification Skipped` block → Step 1.5 (`phases/setup.md`);
  - no RESEARCH document → 2a;
  - RESEARCH document, but no "Research phase complete" note from the completion subagent → 2a's completion spawn;
  - no `CRITICAL-RESEARCH-*` review for this feature → 2b, then 2c. Skip 2b when an `## ADR Candidates` entry is already there; re-running it is safe (it writes no record, and the body declines a decision that already has one);
  - the review has no "Findings Addressed" section → 2d;
  - otherwise → 2e: commit, then `## Research - Accepted`.
- If no phase info → nothing to resume. When the latest record is a `Finished:` line, tell the user that feature is done and show the line. Otherwise start from Step 0 (read `phases/setup.md`).

## Error Handling

**A second-model review run that fails is not handled here.** `references/second-model-review.md` §3 has its own rule — run once more, then that step on the Claude route, recorded and told to the user — and it never stops the flow. The rule below applies to subagents, the Claude-route reviewer included.

If a subagent fails or returns incomplete results, the orchestrator:
1. Logs the failure in `progress.md`.
2. Re-spawns the subagent with additional context about what went wrong.
3. If the same subagent fails twice, stops and informs the user.

## Why the safety-net is count-based, not percentage-based

A spawned subagent has no first-class way to read its own context utilization — `/usage` is a harness slash command available only to the top-level interactive Claude, and the API returns token counts to the harness, not the model. Any self-audit a subagent performs produces output tokens that land back in its own context, partially eating the budget it is trying to measure. Count-based triggers (file Reads) are nearly free to evaluate (rule application, not deliberation), are inspectable in the counter file, and don't require the subagent to know anything its harness won't tell it. Because subagents do not spawn in this flow (a platform limit on Claude Code ≤2.1.171; a deliberate design rule from 2.1.172, which allows nesting to depth 5 — see `proposals/nested-subagents-analysis-2026-06-12.md`), there is no nested-subagent count — Reads is the whole signal. Defaults (Reads >15, or >20 for implementation chunks) are tunable without changing the protocol.
