# Hostile Input — how code treats input it does not control

The one definition of the rules an implementer follows wherever the code reads something it does not control. The planning body (`bodies/planning.md`) reads §1–§2 to write the spec's `### Input Boundaries` cases; the implementer bodies — the whole-feature implementer and each of its chunks (`bodies/implementation.md`) and the per-slice implementer (`bodies/slice-start.md`) — and every fix prompt read it to build and test them. Each reads it at the `HOSTILE_INPUT` path in its prompt and never restates it.

**Why this exists.** In feature 002 (a ledger script that reads JSON files, its own review files and git) about forty review findings were one of a few kinds: text split or trimmed differently from its format, a rejected value printed back in an error, a failed git call read as "nothing there", a symlink followed, a parser exception escaping as a traceback. None was a spec requirement; each was found by a reviewer feeding the code an input the implementer never tried, and each took a fix round. These rules are those findings turned round, so the first build already holds them.

**Not here:** a spec's security rules — what a user may do, see or be refused — are `references/security-verification.md` (SECURITY) §1 and §3, and are proven as it says. A rule below can be one of them too; then it is proven there, not twice.

---

## 1. Where the rules apply

An **input boundary** is every place the code takes in something it did not produce in the same run: command-line arguments and environment variables, files and folder names, another tool's output (git, a shell command, a subprocess), a network reply, a model's answer, and records an earlier run or another program wrote — the application's own data files included. The design brief's `Inputs it does not control:` line (in `## How it will work`) names the ones the owner approved, and the spec's `### Input Boundaries` gives each one's cases and outcomes; a boundary you find in the code that neither names is built to these rules too. Each rule below applies at each boundary the feature adds or changes. Code behind a boundary may trust what the boundary checked.

## 2. The rules

These decide **how** a reader is built, never **what** it accepts: what an input may be, and what happens to one that is wrong, is the SPEC's. Where the SPEC is silent, build a new reader to these rules. Never apply one to an existing reader where it would change what an input that works today does — that is a change beyond the request (TIERS → Beyond the request): leave it and name it in your return.

1. **Split and trim by the format's grammar.** Split and trim exactly where the input's format says, and nowhere else — find what it allows (LF only, CRLF, bare CR) before choosing how to split. The trap is a function that does more than the format: Python's `str.splitlines()` also splits on Unicode line separators and control characters; a bare `strip()` removes every kind of whitespace; a shell `$(…)` drops trailing newlines. A path or a name is never trimmed unless its format says so: a folder may end in a space or a newline.
2. **Match a name exactly.** A name, heading, file name, folder or id is accepted by equality, an anchored full match, or the format's own parser — never by a prefix, a suffix, or a glob, unless the SPEC says the input is a pattern. `REVIEW-other.md`, `## Findings appendix` and `preview-9.0.0` are not the names they start like. When one program writes a value and another reads it back, both use the same check.
3. **Absence comes only from a command that said so.** Read every subprocess's exit status by that command's own contract: "none" only from the outcome it documents as none found (`grep` exits 1 for no match; `git` exits 0 with empty output), and every other failure is an error, reported as one. When several reads must describe the same thing (a branch, a file), resolve it once (a commit SHA, an open file) and read everything from that. Ask the tool for a location (`git rev-parse --show-toplevel`) instead of assuming the current folder is it.
4. **Decide links on purpose.** Where a path the code reads, writes or runs lies in a place someone else can write — a repository, an upload folder, a plugin cache — decide what a symlink there means (the path itself or a folder above it): when the SPEC does not say, refuse it in a new reader, and name the choice in your return. A link the code follows is resolved, checked to lie inside the folder it must stay in, and then the **resolved** path is used, never the original; where a folder on that path can change while the code runs, open the file first and check what was opened (its real path or its device and inode) — a check of the path and a later open can see two different files. System paths outside that place (`/tmp` on macOS) are not in question. In a git tree, an entry of mode `120000` is a link, not file content.
5. **Every exception ends in a defined outcome.** Each exception a parser, a file read or a subprocess can raise at the boundary — a missing file, a folder where a file was expected, bad encoding, malformed JSON, a duplicate key — ends in the outcome the SPEC gives for that case (a missing optional file may mean "use the defaults"; an unreadable one is an error): never a traceback, never an exit the SPEC does not name. Where the language itself has a limit the input can reach — recursion depth on deep nesting, Python's digit limit on `int()` — reaching it ends in that outcome too. Invent no size limit of your own; one the SPEC gives is enforced.
6. **Never print a rejected value back.** An error names the field, the rule and the place (a line number, a key) — never the value that broke it, nor a path or message taken from an exception (`OSError.filename`, a library's error text). A name you must show (a folder, an alias) goes through one display function that escapes whatever can change the structure of the output it goes into — line breaks and control characters in line-based text, and that format's own delimiters — and keeps other printable text: `München` stays `München`.
7. **Write so a reader never sees half a file.** Publish a file by writing a temporary file in the same folder and renaming it over the target. To change one record, copy the file's bytes into the temporary file with only that record's bytes replaced, then rename; parsing the file and writing it all out again can change what was stored. Where two runs can update the same file, hold a lock from the read to the rename, or the later rename puts back what the earlier run replaced.

## 3. Testing them

A guard is tested when the SPEC names its case — an entry of `### Input Boundaries`, or another REQ, EDGE or FAIL whose outcome it holds — or when it holds a security rule; then SECURITY §3 decides, one test per path the rule must hold on. Then test it with the hostile input really present — a real file with the bad bytes, a real symlink, a git command that really fails (a missing ref) — through the real entry point, not a mock of the reader, asserting the outcome the SPEC gives. Among the tests of named cases, give each guard its own: a fixture that trips two guards at once (a symlinked file inside a symlinked folder) passes when either guard is removed. **A guard the SPEC names no case for gets no test of yours** (TEST_INTEGRITY §1, *How many tests*): record it under `### Implementation Deviations` in the IMPLEMENTATION-PLAN as a case the spec is missing — boundary, input, the outcome you built — and name it in your return, so the owner can add it.
